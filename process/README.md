# 개발 과정 기록

앱을 어떤 과정을 거쳐 만들었는지 정리한 폴더입니다. 역할 구조와 스킬 자체는 [orchestration/](../orchestration/README.md)에 있습니다.

| 문서 | 내용 |
|---|---|
| [case-studies.md](case-studies.md) | 실제로 부딪힌 문제 4가지: LLM 시각 오추출, 명세와 API 약관의 충돌(Astra 호출), 성능과 약관 사이의 절충, 검증 구조가 잡아낸 오케스트레이터의 실수 |
| [review-log.md](review-log.md) | 작업별 독립 검토 판정과 수정 흐름 |
| [examples/01-task-review-fix/](examples/01-task-review-fix/) | 한 작업의 실제 양식 흐름: 지시서 → 작업 결과 → 검토 실패 → 수정 후 검토 통과 |
| [examples/02-astra-escalation/](examples/02-astra-escalation/) | 유일한 Astra 호출의 요청서와 지시서(명세 대 KOBIS 이용약관) |

예시 문서는 실제 파일에서 로컬 경로를 `<workspace>`·`<scratchpad>`로, KOBIS 실제 영화명을 `<영화명>`으로, 과정 명세서의 장·절 번호를 "과제 요구사항"으로 바꾼 것 말고는 손대지 않았습니다. 그래서 문장이 정돈돼 있지 않고 내부 작업 ID가 그대로 나옵니다.

## 타임라인 (2026-11-18)

| 구간 | 한 일 |
|---|---|
| 기본 구현 | Tool 4종 → 이벤트·저장소 → 메인 Agent → API·화면 → 문서 초안. 일꾼 3개를 병렬로 돌리고 검토는 작업별로 진행 |
| 실제 키 검증 | KOBIS·카카오·TMDB 키를 발급하고 외부 API 3종과 GMS LLM 호출을 확인. 대표 시나리오를 돌려 실패 안내 누락, 시각·날짜 오추출, 지연 문제를 찾아 수정 |
| 약관 대응 | 코드·문서 검토 실패 후 Astra 호출. 저장은 사실만, 제출 샘플은 합성 데이터, 출처 독립 표시로 재설계 |
| 마무리 | 최종 문서 검토 → 심화 F3020(이상 징후 판단) 추가 → 공개용 정리 |
