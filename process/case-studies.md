# 개발 과정 사례

하루(2026-11-18) 동안 [astra-led-pipeline](../orchestration/README.md)으로 만들며 실제로 부딪힌 문제를 네 가지로 정리했습니다. 각 사례는 문제를 어떻게 발견했고, 어떻게 판단했고, 무엇을 바꿨는지 순서로 적었습니다. 결정 번호(D37 등)는 [결정 기록](../app/docs/DECISIONS.md)과 이어집니다.

## 1. 테스트는 통과했는데 LLM이 시각을 잘못 읽었다

**발견.** 요청 분석은 LLM 구조화 출력으로 했고, 대역 LLM으로 짠 단위 테스트는 모두 통과했습니다. 그런데 실제 키로 대표 시나리오를 돌리자 재계획 시나리오가 재계획을 하지 않았습니다. 이벤트 로그를 보니 실제 모델이 "4시 35분 전에 끝나는"의 종료 시각을 19:25로 뽑아 시간 창이 넓어져 있었습니다. 다시 돌렸을 때는 19:55였습니다. 다른 실행에서는 "토요일"을 날짜로 뽑지 않아 오늘 날짜로 처리됐습니다.

**판단.** 시각과 날짜는 판단 결과를 직접 바꾸는 값이라, 확률적인 추출에 맡길 수 없다고 봤습니다. 메시지에 명시된 한국어 시각·날짜 표현은 코드 규칙(정규식)으로 뽑아 LLM 값보다 우선하고, 덮어쓴 경우 이벤트에 `rule_overrides`로 남기기로 했습니다(D37). 의도 분류와 지역·장르 추출은 LLM에 그대로 둡니다.

**검토가 찾은 부작용.** 독립 검토자가 규칙을 직접 시험해 오탐을 찾았습니다. 규칙이 맞는 LLM 값을 틀린 값으로 덮는 경우입니다.
- "밤 12시까지"를 정오로 읽음
- "그럼 내일 말고 토요일은?"에서 앞쪽 "내일"을 날짜로 채택
- "다다음 주 월요일"을 다음 주로 읽음

**결과.** 규칙이 모호하면 아예 값을 내지 않고 LLM 값을 유지하도록 바꿨습니다(D40). 모호한 경우란 밤·새벽 시각, 날짜 표현이 둘 이상인 경우, "말고·지난·다다음" 같은 표현, "N시 10분 전"처럼 두 가지로 읽히는 표현입니다. 이후 실제 실행에서 모델이 다시 19:55를 냈을 때 규칙이 16:35로 바로잡은 기록이 [재계획 사례 로그](../app/docs/logs_sample/)에 남아 있습니다.

**배운 점.** 대역 LLM 테스트는 "LLM이 맞게 답한다"는 가정을 검증하지 못합니다. 결과를 바꾸는 값은 코드로 검증 가능한 경로를 두되, 규칙이 확신하지 못할 때 물러나는 조건까지 설계해야 오탐이 생기지 않습니다.

## 2. 명세와 외부 API 약관의 충돌

**발견.** 과제 요구사항은 실행 로그(Tool 호출·응답 이벤트)를 저장하고 대표 실행 로그를 제출하도록 했습니다. 그런데 KOBIS 오픈 API 이용약관 제6조 제2항은 "결과를 실시간으로 사용하여야 하며, 결과를 복제 또는 저장하거나 제3자의 서비스로 재전송할 수 없다"고 정합니다. 처음 구현은 실행 로그와 제출 샘플에 영화명·러닝타임 요약을 담고 있었고, 성능 개선으로 넣은 6시간 상세정보 캐시도 KOBIS 결과를 보관했습니다.

**판단.** 처음에는 오케스트레이터가 캐시만 TMDB로 제한하는 부분 결정을 했습니다. 그러자 문서 검토가 "이용 조건 준수를 '적용'으로 쓴 것은 과장"이라며 실패 판정을 냈습니다. 필수 요구사항과 약관이 정면으로 부딪히는 문제라 오케스트레이터 혼자 결론 내리지 않고, 스킬의 에스컬레이션 조건 3(명세·설계 해석이 갈림)으로 Astra를 호출했습니다. 이 호출이 이번 작업의 유일한 Astra 호출입니다. 실제 요청·지시서는 [예시](examples/)에 있습니다.

**Astra 지시(그대로 실행).**
- 실행 로그에는 호출과 판단이 일어난 **사실**만 저장합니다. 저장하는 것은 `call_id`, 제공자, 성공 여부, 실패 코드, 소요 시간, 단계, 의도 판단, 재계획 사유입니다. KOBIS 유래 제목·코드·순위·러닝타임과 자유문장 요약은 저장하지 않습니다.
- 세션 Memory에는 사용자 조건과 처리 상태만 둡니다. KOBIS 결과의 요청 간 캐시는 없습니다.
- 계획 저장 폼은 KOBIS 후보로 자동 채우지 않고 사용자가 입력합니다.
- 제출 샘플은 **합성 데이터**로 전체 실행을 기록하고(`--mode fixture`), 실제 API 증빙은 **이벤트만** 기록합니다(`--mode live`).
- 화면은 KOBIS 결과를 출처 라벨이 붙은 독립 영역에 표시하고, TMDB 승인 로고와 고지 문구를 넣습니다.

되돌릴 수 없는 작업(기존 실행 로그 60행 삭제, 기존 샘플 교체, 로고 파일 내려받기)은 사용자에게 승인을 받고 진행했습니다.

**검토가 찾은 남은 경로.** 지시를 구현한 뒤에도 독립 검토가 두 곳을 더 찾았습니다.
- 시나리오 실행 스크립트가 LangSmith 추적을 끄지 않아, 환경변수가 켜져 있으면 KOBIS 결과가 담긴 그래프 상태가 외부로 나갈 수 있었습니다.
- 화면이 출처별 영역 아래에 KOBIS·계산·카카오 정보가 섞인 답변 원문 단락을 덧붙이고 있었습니다.

둘 다 고쳤습니다.

**결과.** 실제 키로 요청한 뒤 DB의 실행 로그를 조회해 KOBIS 유래 값이 0건임을 확인했습니다. 이용 조건 항목(NF3007)은 키별 호출 한도처럼 확인하지 못한 조건이 남아 있어 문서에 "부분 적용"으로 정직하게 남겼습니다.

## 3. 성능을 올리다가 약관 때문에 일부를 되돌린 과정

| 단계 | 관찰 | 조치 |
|---|---|---|
| 1 | 재계획 상한 시나리오가 상세 조회 48건을 하나씩 호출해 38.5초 | `ThreadPoolExecutor` 병렬화. 이벤트는 완료 순서가 아니라 후보 순서로 발행해 로그를 결정적으로 유지 → 11.5초 |
| 2 | 화면 실행 중 KOBIS 상세 10건 중 4건이 약 10.4초 뒤 타임아웃 | 같은 10건을 직렬·병렬 4·병렬 8로 반복 측정. 직렬에서도 12.1초 회차가 나와 병렬 탓이 아닌 간헐 지연으로 판단 |
| 3 | 지연 1건이 응답 전체를 10초 이상 끌어올림 | HTTP 타임아웃 5초 + 타임아웃·연결 오류에만 1회 재시도, 공개 API 부하를 줄이려 병렬 수 4로 축소 |
| 4 | 같은 영화 상세를 요청마다 다시 조회 | 성공한 상세만 6시간 캐시(요청 간) |
| 5 | KOBIS 약관상 결과 저장 불가([사례 2](#2-명세와-외부-api-약관의-충돌)) | 요청 간 캐시는 TMDB만. KOBIS는 한 요청 안의 재계획용 캐시만 유지 |

마지막 단계는 성능을 일부 되돌린 선택입니다. 응답 시간보다 이용 조건 준수를 우선한다는 판단을 결정 기록(D38~D40)에 남겼습니다.

## 4. 검증 구조가 오케스트레이터의 실수를 잡아낸 사례

역할을 나눈 효과가 가장 분명하게 보인 부분입니다. 아래는 모두 오케스트레이터(필자 쪽 Claude)가 만든 실수이고, 다른 역할이 기록을 근거로 바로잡았습니다.

- **지시서의 계산 실수 2건을 일꾼이 바로잡았습니다.**
  - 러닝타임 200분 영화가 15:00~19:00 창에서 "불충족"이라고 예시를 적었는데, 광고 10분을 더해도 18:30에 끝나 충족입니다.
  - 주간 박스오피스 기준일 예시를 11-16(월요일)으로 적었는데, 공식대로라면 직전 일요일인 11-15입니다.
  - 일꾼은 명시된 공식대로 구현하고 차이를 작업 결과서에 보고했습니다.
- **검토자가 확인 시각 오기를 DB 기록으로 바로잡았습니다(2건).** 오케스트레이터가 검토 요청서에 화면 확인 시각을 "14:5x", "15:1x"로 적었습니다. 검토자는 실행 로그의 타임스탬프와 파일 수정 시각을 대조해 실제로는 14:46, 15:05~15:06임을 밝혔고, 문서에는 기록 기준 시각만 남겼습니다.
- **검토자가 재현 탐침으로 설계 결함을 찾았습니다.** 실행 로그 상세를 seq 순으로 정렬하던 초기 구현은 서버가 재시작되면 같은 세션의 seq가 1로 돌아가 이전·이후 실행 이벤트가 섞였습니다. 단위 테스트에는 없던 경우를 검토자가 재시작을 흉내 낸 탐침으로 재현했고, 저장 순서 정렬로 고쳤습니다.
- **시나리오 설계 실수도 실제 실행에서 드러났습니다.**
  - 재계획을 보여 주려던 시나리오의 시간 창이 너무 넓어 재계획이 일어나지 않았습니다. 실제 데이터의 러닝타임 분포를 보고 95분 창으로 다시 설계했습니다.
  - 영화관 검색 실패를 유도하려고 쓴 가상 지명을 LLM이 지역으로 뽑지 않아, 실제 영화관이 없는 지명으로 바꿨습니다.

이 사례들 때문에 문서의 실행 결과는 모두 "실제로 실행해 기록에서 확인한 값"만 적는다는 원칙을 끝까지 유지했습니다.
