# 설계 결정 기록

2026-11-18에 기록한 선택과 변경 이유입니다. 이전 선택이 바뀐 경우 후속 결정 ID를 함께 적었습니다.

## 서비스 구성

- D01 · 후보 조회, 시간 계산, 실행 로그와 계획 관리를 먼저 구현했습니다. 이후 실행별 이상 판정·진단(F3020)을 추가했습니다(D44).
- D02 · 서비스는 `backend/`, `frontend/`, `docs/`로 나눴습니다.
- D03 · 개발 중에는 작업 트리에서 변경을 확인했습니다. 커밋은 사용자가 별도로 진행하기로 했고, 원격으로 반영하지 않았습니다.
- D04 · 변경 이유는 이 문서에, 동작을 확인한 근거는 검증 결과에 기록했습니다. [검증 결과](검증결과.md)
- D10 · 후보 목록과 러닝타임이라는 확인 가능한 데이터가 있는 영화 관람을 선택했습니다. 사용자가 정한 시간 안에 관람할 수 있는 후보를 계산하고, 실제 상영 여부와 시간은 영화관에서 확인하도록 안내합니다. 건강이나 금융처럼 별도 면책 문구가 필요한 판단은 제공 범위에 두지 않았습니다.
- D11 · KOBIS의 일별·주간 박스오피스와 영화 상세를 후보·러닝타임·장르 확인에 사용합니다. 카카오 로컬을 영화관 위치에, TMDB의 국내 현재 상영작과 상세를 후보 보충에 사용합니다. 설정 변수명은 각각 `KOBIS_API_KEY`, `KAKAO_REST_API_KEY`, `TMDB_API_KEY`입니다.
- D12 · 자연어 분석에는 SSAFY GMS를 사용합니다. `ChatOpenAI`는 `GMS_MODEL`, `GMS_KEY`, `GMS_BASE_URL`을 읽으며 기본 모델은 `gpt-5.4-nano`입니다.
- D13 · SQLite 파일 `backend/data/planner.db`에 `plans`와 `run_logs`를 저장하도록 구성했습니다. 실행별 판정과 진단을 도입하면서 `anomaly_reports`와 `anomaly_diagnoses`를 추가했습니다(D44).
- D14 · 화면은 바닐라 HTML·CSS·JavaScript로 작성했습니다. 개발 환경에서는 `python -m http.server 5500`으로 화면을 열고 `http://localhost:8000`의 백엔드와 연결합니다.

## Tool과 조회 날짜

- D20 · 모든 Tool 응답은 `{"ok": true, "data": ...}` 또는 `{"ok": false, "error": {"code", "message"}}` 형식입니다. 제공자 응답은 쓰는 필드만 정규화하며 누락된 선택값은 `None`으로 둡니다. 실행 예외는 공통 실패로 처리하고 오류 메시지에는 키 값과 키가 들어간 URL을 싣지 않습니다.
- D21 · 실패 코드는 `BAD_ARGUMENT`, `INVALID_KEY`, `NOT_FOUND`, `NO_DATA`, `UPSTREAM_ERROR`, `NO_RUNTIME`(러닝타임 없음), `NO_RESULT`(장소 검색 결과 없음)로 구분합니다.
- D22 · 레지스트리에 `external`과 `local` 구분을 두고, 네 외부 조회 Tool만 등록합니다. 관람 계획 저장에는 사용자 입력을 받는 FastAPI 경로를 사용합니다.
- D23 · 날짜를 생략하면 KST 오늘을 요청일로 사용합니다. 일별 박스오피스 조회일은 요청일과 KST 어제 중 빠른 날짜입니다. 다른 날짜의 집계를 조회하면 `estimated=true`와 `note`로 알립니다.
- D24 · 주간 박스오피스는 요청일이 이미 끝난 주에 속하면 그 주를, 그 이후의 날짜라면 가장 최근에 끝난 주를 조회합니다. 범위는 월~일입니다. `week_range`에 실제 집계 범위를 반환하며 대체 시 `estimated=true`와 `note`를 제공합니다. Tool의 출력 구조는 레지스트리의 `output`과 `describe_tools()`에서 조회할 수 있습니다. [Tool 정의서](Tool정의서.md)

## 관람 판단과 응답

- D30 · 필요 시간은 러닝타임과 기본 광고 시간 10분(`AD_MINUTES`)의 합입니다. 시작 가능 시각에 필요 시간을 더한 값이 종료 제한 이내면 충족입니다. 종료 제한에서 필요 시간을 뺀 시각을 늦어도 시작할 수 있는 시각으로 표시합니다.
- D31 · 종료 제한을 주고 시작 가능 시각을 생략했으면 Tool 호출 전에 되묻습니다.
- D32 · 충족 후보가 0개면 일별 박스오피스에서 주간 박스오피스, TMDB 국내 현재 상영작 1페이지, 2페이지 순으로 옮겨 갑니다. 재계획 기본 상한은 `REPLAN_LIMIT=3`입니다. 앞선 풀의 후보를 중복 제거하고 요청 중 조회한 상세를 재사용합니다. 후보 목록 인증 오류(`INVALID_KEY`)는 설정 안내로 마무리합니다.
- D33 · 요청 의도를 `plan_movie`(관람 계획), `fact_query`(순위·러닝타임·위치 등 사실 조회), `smalltalk`(인사·사용법 등)로 나눕니다. 일반 대화는 Tool을 호출하지 않습니다.
- D34 · 초기 설계의 세션 메모리에는 직전 조건과 추천 영화명·러닝타임 등을 포함한 결과 요약을 두었습니다. 후속 요청에서는 바뀐 조건만 덮어쓰는 방식을 유지하고, 보관 필드는 D41에서 사용자 조건과 처리 상태로 제한했습니다.
- D35 · 요청 의도·분류 이유·조건을 구조화하는 데 LLM을 사용하기로 했고, 초기 설계에서는 답변 문장 다듬기도 선택지로 두었습니다. 현재는 GMS 분석 결과를 바탕으로 계산·판단·재계획과 답변 구성을 코드에서 처리합니다. 로깅 Agent의 이벤트 수집·저장과 판정은 규칙으로 처리하고, 이상 실행 원인 진단에만 별도 모듈이 GMS를 호출합니다(D44).
- D36 · 처음에는 세 화면 하단에 KOBIS·TMDB·카카오 출처와 TMDB 고지를 텍스트로 표시했습니다. 크레딧과 출처별 영역은 D43에서 갱신했습니다. 처리되지 않은 서버 예외는 traceback을 서버에 남기고 화면에는 공통 오류 문구를 표시합니다.
- D37 · 2026-11-18 S2 실측에서 GMS가 “4시 35분 전에 끝나는”을 `end_by=19:25`로 해석했습니다. 명확한 시작·종료 시각 표현에 코드 규칙을 우선하고, 실제 변경은 `llm_decision.payload.rule_overrides`에 기록하기로 했습니다. 1~11시는 오전·아침·새벽 표현이 있으면 오전, 그 외에는 관람 맥락에 따라 오후로 해석합니다. 당시 날짜는 GMS 분석을 사용했습니다. 날짜 규칙과 모호한 표현의 처리 기준은 D40에서 추가했습니다.
- D38 · KOBIS는 HTTPS를 사용합니다. 기본 타임아웃은 5초이고 `Timeout`·`ConnectionError`만 1회 재시도합니다. 상세 조회는 `ThreadPoolExecutor`에서 최대 4건씩 병렬 실행하고 후보 순서로 호출과 결과를 발행합니다. 조회 실패는 답변에 이유를 표시합니다. 상세 병렬화 전 기록의 최장 사례는 S3의 38.5초였습니다. 병렬화 후 요청 간 캐시를 도입하기 전 기록의 최장 사례는 S1의 23.8초였습니다. [비기능 검증](검증결과.md#비기능)
- D39 · 2026-11-18 실측에서 KOBIS 상세가 직렬·병렬 모두 간헐적으로 5초 이상 지연되거나 실패했습니다. 상세 성공 응답을 정규화해 별도 프로세스 캐시에 6시간 보관하기로 했으며, 요청 간 캐시 적용 출처는 D40에서 제한했습니다. 캐시 적중은 Tool 호출 수에 포함하지 않고 `execute` 단계 종료 이벤트의 `cache_hits`에 남깁니다.
- D40 · 요청 간 서비스 캐시는 성공한 **TMDB 상세만** 보관합니다. KOBIS 상세는 KOBIS 이용약관 제6조 제2항의 실시간 사용과 복제·저장 제한을 적용해 요청 중에만 재사용합니다. 날짜도 명확한 한국어 표현은 KST 기준 규칙값을 우선합니다. 날짜 표현이 둘 이상이거나 ‘말고·아니고·대신·지난·저번·다다음·내일모레’처럼 모호한 경우, 또는 ‘밤·저녁 12시’, ‘밤·새벽 1~5시’, 종료 조건의 ‘N시 M분 전’에서 M이 20 이하인 경우에는 정규화된 LLM 값을 사용합니다. 실제 변경만 `rule_overrides`에 기록합니다. [외부 API 출처와 이용 조건](../README.md#외부-api-출처와-이용-조건-nf3007), [날짜·시각 보정](Agent설계.md#요청-분석과-날짜시각-보정)

## 데이터 저장과 출처 표시

- D41 · KOBIS 결과는 한 요청의 실시간 계산과 화면 표시에만 사용합니다. 세션 Memory는 사용자 조건과 처리 상태를 이어받습니다. 로그에는 메인 Agent가 발행한 구조화 이벤트만 저장합니다. KOBIS의 제목·코드·순위·러닝타임과 조회 결과 요약은 그 필드에 포함하지 않습니다.
- D42 · 계획은 독립적으로 입력한 영화명과 사용자가 정한 일정을 저장합니다. 합성 모드(`--mode fixture`)는 최종 답변과 구조화 이벤트, 기대 비교를 남깁니다. 실호출 모드(`--mode live`)는 실제 실행의 구조화 이벤트를 남깁니다. [대표 시나리오](검증결과.md#대표-시나리오)
- D43 · KOBIS 결과를 ‘영화진흥위원회 영화관입장권통합전산망 · 통합전산망 오픈 API’ 출처와 함께 독립 영역에 표시합니다. 세 화면의 크레딧에는 TMDB 승인 로고(`frontend/img/tmdb_logo_long.svg`)와 공식 고지 문구를 함께 표시합니다. 2026-11-18 표시·저장 방식을 전환할 때 사용자 승인 후 기존 로그 2세션 60행을 세션 삭제 API로 정리하고 0행을 확인했습니다. 관람 계획과 혼합 출처 사실 조회에는 출처별 영역을 사용합니다. 제외 후보는 최대 10건, 영화관은 최대 5곳, 조회 근거는 제공자별 최대 10행을 표시하고 나머지 근거 수를 안내합니다. [출처 표시와 저장 확인](검증결과.md#출처-표시와-저장-확인)

## 실행 이상 판정과 진단

D44 · 2026-11-18부터 세션 로그를 `analyze` 시작 이벤트를 기준으로 실행 단위로 나누고 다음 규칙으로 판정합니다.

- 같은 Tool·입력 조합을 반복 호출하면 이상입니다. 발행 단계에서 요청 내 메모리로 비교하고, 반복 이벤트에 앞선 호출의 `call_id`를 `duplicate_of`로 연결합니다. 비교용 입력 전체나 해시는 저장하지 않습니다.
- 재계획이 `REPLAN_LIMIT`에 도달하면 경고, 초과하면 이상입니다.
- 최초 계획과 재계획에 없던 Tool 호출은 이상입니다. 계획·분석 시작·응답 종료 또는 필요한 호출·결과 이벤트가 빠지면 근거 누락을 우선해 `undetermined`로 판정합니다. 근거가 충분한 실행은 규칙에 따라 `normal` 또는 `anomaly`로 판정합니다.

`anomaly` 실행만 백그라운드에서 GMS로 원인을 진단하며, 진단 결과는 최대 3문장입니다. 판정과 진단을 별도 테이블에 저장하고 실패해도 판정과 이벤트를 보존합니다. 진단은 경고 수에 포함하지 않습니다. 다음 요청을 분석할 때 같은 세션의 직전 판단을 `llm_decision`에 참조로 남깁니다. [이상 징후 검증](검증결과.md#f3020-이상-징후)
